# Batch / Multiple / Flexible 的区别

## 简单概括

批量筛选让配体逐个独立运行；共同对接让两个配体在同一次搜索中优化；柔性受体允许指定侧链参与搜索。它们的输入要求和评分含义不同。

---

## 三个功能的入口

批量筛选使用配体队列；多配体共同对接要求恰好两个已准备的配体；柔性受体则需要在准备阶段生成柔性侧链文件。

如果希望每个配体有各自的评分，应使用批量筛选。共同对接给出的是联合体系评分。柔性受体改变的是受体侧链的搜索自由度，使用前还要核对当前协议的组合限制。

---

## 三种方式的对照

```text
Batch（串行批量）
  一个受体 + 很多配体 → 一次一个，各自独立运行、各自独立评分

Multiple（多配体共同对接）
  一个受体 + 恰好两个配体 → 一次搜索，一起跑，只有一个联合评分

Flexible（柔性受体）
  一个受体（侧链可变） + 一个配体 → 让受体的一部分也参与搜索
```

---

## 对照表

| 维度 | 串行批量 | 多配体共同对接 | 柔性受体 |
|---|---|---|---|
| 变的是什么 | 配体**数量** | 配体**数量与组合方式** | **受体**的柔性 |
| 配体数 | 1–500 | **恰好 2** | 1 |
| 是否共用一次搜索 | 否，每个配体独立 | **是，同一次搜索** | 是（受体侧链一起搜） |
| 评分口径 | 每个配体各自的 affinity | **一个联合评分** | 常规 affinity |
| 受体柔性 | 必须刚性 | 必须刚性 | 有柔性侧链 |
| 运行模式 | 必须全局对接 | 必须全局对接 | 三种模式都可能 |
| 上限 | 500 配体 / 64 CPU / exhaustiveness 128 / num_modes 50 / Box 126 Å | — | — |
| 成熟度 | 当前源码可用 | **experimental** | 当前源码可用 |

---

## 串行批量筛选（Batch）

它解决的是"**我有一堆候选分子，想都跑一遍**"。

关键性质：**串行**。

```text
配体 1 → 运行 → 记录
配体 2 → 运行 → 记录
配体 3 → 运行 → 记录
...
```

- 一次只跑一个配体；
- 每个配体有**独立**的配置、独立的 affinity、独立的失败记录；
- 失败的项可以重试，但重试次数有限制；
- 整个队列复用**同一组冻结的受体与搜索范围**。

每一次尝试都会单独留下记录：

```text
screening/attempts/<配体>/attempt_001/
   receptor.pdbqt   ligand.pdbqt   config.txt
   out.pdbqt        stdout.txt     stderr.txt     log.txt
   attempt.json
```

产出：完整 CSV、Top N 结果、逐配体最佳构象、整批 Markdown 记录，以及只读的归档历史。

它的限制很明确：

- 只支持**全局对接**（不接受评分 / 局部优化）；
- 只支持**刚性受体**；
- AD4 只走**标准 maps**，不支持 AD4Zn 或水合；
- 不使用 `autobox`。

有一点务必要清楚：

> 批量筛选**不是**"自动虚拟筛选流水线"。某一个配体失败了，**不代表**它不能结合，只说明这一次运行没成功。

---

## 多配体共同对接（Multiple）

它解决的是另一类问题："**这两个配体如果同时存在，会怎样？**"

关键性质：**一次搜索，联合评分**。

```text
受体 + 配体 1 + 配体 2
        ↓
一次 Vina 搜索
        ↓
每一条 Mode 都是"一组联合构象"
        ↓
只有一列联合评分
```

所以：

- **不拆分**成员 affinity；
- **不推断**"配体 1 贡献了多少"；
- **不能**把成员数或组成不同的联合任务直接比分数。

它的限制也明确，而且比批量更严：

| 限制 | 说明 |
|---|---|
| 配体数必须是 2 | 多了少了都不行 |
| 必须刚性受体 | 不支持柔性侧链 |
| 必须全局对接 | 不支持评分 / 局部优化 |
| 评分协议 | Vina / Vinardo，或标准 AD4 maps |
| 预计算 Vina/Vinardo maps | **不支持** |
| `autobox` | **不支持** |

它**不会**自动替代串行批量筛选 —— 两者用途不同，不能互换。想知道"每个配体各自多强"，就得用批量。

---

## 柔性受体（Flexible）

它改变的不是配体，而是**受体参与搜索的部分**。

```text
常规刚性受体
  受体固定不动，配体在 Box 里搜

柔性受体
  受体的一部分（你指定的侧链）也能动
  配体 + 柔性侧链 一起参与搜索
```

实现上：

- 受体准备会产出**三件套**（刚性部分、柔性部分、受体记录），准备记录在 `preparation/flexible_receptor/`，产物在 `prepared/flexible_receptor/`；
- 运行时额外传一个柔性侧链文件（命令行上的 `--flex`）；
- 只有三件套完整性校验通过，才允许把受体切成柔性模式。

几个容易踩的点：

- **必须先把三件套准备齐**，否则根本切不到柔性；
- 从柔性切回刚性时，相关的 maps / 协议设置会被**清空** —— 这是为了避免出现"协议与受体不匹配"的状态，不是 bug；
- 与 **Vina / Vinardo 预计算 maps 不兼容**（源码明确拒绝这个组合）；
- 如果同一次运行里还开了评分模式，`unbound_energy` 会被禁用。

柔性的代价很直接：搜索空间明显变大。可旋转的东西多了，同样的 `exhaustiveness` 下想搜透就更难，跑得也更久。

---

## 什么时候用哪个

```text
有一批候选分子要各自跑一遍         → 串行批量
关心两个配体同时存在时的联合行为   → 多配体共同对接
怀疑口袋侧链会诱导契合、想让它动   → 柔性受体
只是跑一个配体看看                 → 普通单配体全局对接
```

---

## 一条共同的铁律

串行批量与多配体共同对接都要求：

```text
刚性受体
+ 全局对接
+ 不使用 autobox
```

这三条在源码里是**硬校验**，触发时会直接阻止运行并抛出错误码。**不要试图绕过它们** —— 它们守的是"评分口径必须可比"这个前提：受体不完全一样、搜索方式不一样，分数就没有放在一起比较的资格。

具体的错误码见 [高级协议的适用范围](./advanced-protocols.md) 与 [常见错误与恢复](./common-errors-and-recovery.md)。

---

## 总结

Batch、Multiple、Flexible 回答的是三个不同的问题：批量是各自独立地跑，多配体是在一次搜索里一起跑，柔性受体改变的是受体本身；选错方式不会报错，但结果回答的就不是你的问题了。
